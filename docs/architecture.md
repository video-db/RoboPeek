# Architecture

How the packages are built and why. For naming and the package split, see [THESIS_REVIEW.md](../THESIS_REVIEW.md).

## Design rules

| Rule | Applied as |
|---|---|
| Layered, each layer usable alone | reader → format adapter (`Timeline`) → hooks → primitives → `Player` parts → viewers |
| Composition over configuration | Compound `Player.*` parts over a growing prop list |
| Splittable, not just swappable | Composite parts take children; every built-in part = hook + thin markup |
| Controlled or uncontrolled | `value` + `onChange` or `defaultValue` for episode, selected, step, playing, fps, autoNext |
| No global side effects | No `window` listeners, no `history` writes; deep links belong to the app |
| Cheap re-renders | Player state in a store read through selectors; only frame/step-bound parts re-render per frame |
| Separate dependencies | Readers are optional peers of `react`; the root entry imports none, `/rlds` and `/mcap` only their own (checked on the build output by `check:boundaries`) |
| Guided failures | Crossing a boundary throws a message naming the fix: a missing reader, an `Episode`/`Recording` passed as a timeline, a format's part in another format's player |
| Wrappable | Every part: `className`, `ref`, rest props; exported props types |
| Slots where content varies | `renderTitle`, `renderEmpty`, `include`; `renderItem` receives the default as `fallback` |
| Overridable styling | CSS in `@layer robopeek`; `rp-*` classes; `data-*` state; `--rp-*` tokens on `:root`; no `!important` |
| Accessible controls | Play is one button whose label switches Play ↔ Pause (no `aria-pressed`); scrubber is a native range input |
| No guessed data | fps is a display choice (`defaultFps`, 10); RLDS records no rate |

## Package config

Generated by tsdown (`exports` option): the repo-only `robopeek-source` condition points at `src/`, and `publishConfig.exports` drops it on publish.

```jsonc
// packages/react/package.json (as packed)
{
  "name": "@videodb/robopeek-react",
  "type": "module",
  "sideEffects": ["*.css"],
  "exports": {
    ".": "./dist/index.js",
    "./package.json": "./package.json",
    "./styles.css": "./dist/styles.css",
    "./structure.css": "./dist/structure.css",
    "./theme.css": "./dist/theme.css"
  },
  "files": ["dist"],
  "peerDependencies": { "react": "^19", "react-dom": "^19" },
  "dependencies": { "@videodb/robopeek-rlds": "^0.1.0" // workspace:^ in the repo }
}
```

- ESM only, built with `tsdown`; `'use client'` banner on the react build; rlds stays external.
- Not `development` as the source condition: consumers' dev servers resolve that too and would look for unpublished `src/`.
- Vite's CSS `@import` ignores `resolve.conditions`, so `apps/web` aliases `@videodb/robopeek-react/styles.css` to source in `vite.config.ts`.

## MCAP

The reader is `@videodb/robopeek-mcap`; the UI is `@videodb/robopeek-react/mcap` on the shared player. Differences from RLDS:

| Decision | Why |
|---|---|
| One React package, format glue per entry point; no shared core package | The player reads a `Timeline` defined in `react`'s core, so readers stay independent and UI isn't duplicated |
| Player state is `position` in the timeline's `unit` (steps for RLDS, seconds for MCAP) + `rate`; parts select the sample at or before it | Topics tick at different rates and carry real timestamps |
| `Recording` fills in place; `version` + `subscribe()` mark changes | Large files play while they stream; copying tracks per batch would be O(n²) |
| Origin = earliest log time within 60 s of the median of the first 64 camera/chart messages; earlier messages sit at 0 | Latched topics and boot-time clocks (seen: 2.7 s vs 1.7e18 ns in one ROS 2 bag) otherwise stretch the timeline to decades |
| Load = one streaming GET; summary read first by Range | Topics and length show at once; one request beats per-chunk reads on Hugging Face (~0.5 s latency) |
| Frame bytes capped (`maxFrameBytes`); release LRU outside the playhead window; refetch by window | A 1.3 GB, 7-camera file can't sit in a tab. Windows are ~4 MB pieces of whole chunks, two in flight, one window at a time, in-flight ranges subtracted |
| Window pieces parsed with `parseRecord`, channels from the summary | `McapStreamReader` rejects messages whose Channel record is in an earlier chunk (FiftyOne files) |
| H.264 via WebCodecs, decoded forward from the nearest keyframe, 16-frame lookahead, no `flush()` mid-stream | `flush()` makes the decoder require a keyframe next |
| 16-bit PNG depth decoded in JS (`DecompressionStream` + unfilter) | Browsers decode it to its top 8 bits, i.e. black |
| Decoders: `@mcap/core`, `fzstd`, `lz4js`, `@foxglove/rosmsg*`, `protobufjs` | Pure JS, no WASM to configure in consumers' bundlers |
